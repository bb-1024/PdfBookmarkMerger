# 不具合修正・機能追加の進め方

複数件の修正・機能追加を依頼された場合、**1件ずつ**このサイクル全体を完了させてから次へ進む
(まとめて全部実装してからまとめてテスト・コミットする、という進め方はしない)。

## 1. 設計

- 症状・要望から根本原因/実現方法を特定する。UIに関わる変更かどうかを判断する。
- UIに関わる場合、**WPF版・Avalonia版の両方**に同じ変更が必要になる
  (`src/PdfBookmarkMerger.Wpf/` と `src/PdfBookmarkMerger.Avalonia/` の対応するXAML/コードビハインド)。
  片方だけ直して終わらせない。
- 大量データ(しおりツリーの全ノード走査など)を扱う変更の場合、既存の
  `RecomputeChunkSize`(200件)チャンク処理 + `IsBusy`/`BusyProgress` オーバーレイのパターンを
  再利用できないか検討する(`BookmarkTreeViewModel.RecomputeAllPageNumberDisplaysAsync`/
  `ApplyExpandLevelAsync` が実例)。新規にUIをフリーズさせる同期処理を書かない。
- 新しい文言が必要な場合、`Strings.resx`/`Strings.en.resx`/`Strings.cs` の3ファイルを
  同時に更新する計画に含める。

## 2. 実装

- Core/App層(UI非依存)とWPF/Avalonia両フロントエンドを、必要に応じてすべて変更する。
- 新規コマンド(`ReactiveCommand`)を追加する場合、大量ノード処理中(`IsBusy`)を
  CanExecuteに `!IsBusy` として含めることを検討する(`UndoCommand`が既存の参考実装)。

## 3. コードレビュー(自己レビュー)

実装直後に、以下の観点で自分の変更を見直す:

- WPF/Avalonia両方に実装したか(片方だけになっていないか)。
- 大量ノードを走査する新規処理はチャンク処理になっているか(なっていない場合、意図的にそうしたか
  理由を説明できるか)。
- 新規コマンドのCanExecuteは`!IsBusy`を含んでいるか(含めない場合、その理由)。
- i18n文言は3ファイル(resx×2 + Strings.cs)すべてに追加したか。
- 単純化・簡素化できる箇所、不要な複雑さが無いか。

## 4. テスト

- 既存のテストプロジェクトの慣習(`CreateSut`ヘルパー・`FakeDialogService`・機能ごとの
  専用テストファイル)に合わせて、新規/変更した振る舞いのテストを追加する。
- 大量ノードを扱う変更を加えた場合、小規模ツリー(`IsBusy`が一度もtrueにならない)・大規模ツリー
  (チャンク処理されて`IsBusy`がtrue/falseを経る)の両方を検証するテストを追加する。
- 実行して確認する:
  ```
  dotnet test PdfBookmarkMerger.slnx -c Debug --nologo
  dotnet test PdfBookmarkMerger.slnx -c Release --nologo
  ```
  失敗が無くなるまでこのステップを繰り返す。

## 5. 設計ドキュメント更新

- 変更内容に対応する `docs/ja/`・`docs/en/` の章(`.md`と`.html`双方)を更新する。
  この時点では **バージョン番号はまだ確定していない場合が多い**(バージョン番号の確定・
  `05-version-history`への追記・タグの hash 記載は、実際にリリースする際に `release` スキルで行う)。
  ただし、変更点の説明そのもの(挙動・設計判断の理由)は実装と同時に書いておく。
- 既存の設計ドキュメントの記述と矛盾しないか(用語・既存の設計判断の説明)を確認する。

## 6. コミット

- 1件の修正・機能追加につき1コミットを作成する(まとめてコミットしない)。
- コミットメッセージは英語・命令形の要約 + 「なぜ」を説明する本文(既存の`git log`のスタイルに合わせる)。
- **明示的に指示されない限り `git push` は行わない。**
- 次の1件に進む前に、ここまでの結果(修正内容・テスト結果)を簡潔にユーザーへ報告する。
