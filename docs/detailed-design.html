01クラス図: ドメインモデル(PdfBookmarkMerger.Core.Models)

PDFsharp型に依存しないプレーンなPOCO群。図には主要メンバーのみを示す(全メンバーは 関数リファレンス参照)。矢印は代表的な関係のみを描画し、それ以外の関係は 図の下に文章で補足する。

has-a / 参照(コレクション・プロパティ)

図に描いていない関係: PdfMergeRequestはFiles (PdfFileEntryのリスト)・Bookmarks (BookmarkNodeのリスト)・Properties (PdfDocumentPropertiesModel)を1件ずつ保持する(結合処理への入力一式)。 PdfFileMetadata.FileEntryIdはPdfFileEntry.Idを指す Guidによる弱参照(オブジェクト参照ではない)。

02クラス図: Coreサービス(PdfBookmarkMerger.Core.Services)

3組のインターフェース+実装(ファイル収集・メタデータ抽出・結合)と、しおりの前処理を担う2つの静的クラス (MissingBookmarkFallback → BookmarkOffsetCalculatorの順に 呼び出すパイプライン)、PDFsharp型変換用のBookmarkDestinationTypeMapperから成る。

実装(implements) / 利用(uses) / パイプライン
依存(dashed) — PDFsharp型への変換で利用

図に描いていない関係: PdfMetadataService・PdfMergeServiceは いずれも生成/入力にCore.Modelsの型(BookmarkNode・ PdfFileMetadata・PdfMergeRequest等、 ドメインモデル図参照)を用いる。MissingBookmarkFallbackと BookmarkOffsetCalculatorはApp層(MainWindowViewModel.ConfirmFilesAsync) から連続して呼び出されるパイプラインであり、Core.Services内部からは互いを呼び合わない。

03クラス図: App ViewModel層(PdfBookmarkMerger.App.ViewModels)

WPF・Avalonia間で完全に共有されるReactiveProperty MVVM層。全クラスはViewModelBaseを 継承するが、図が煩雑になるため継承矢印はMainWindowViewModelのみ代表して描画する。 3つのダイアログ用ViewModel(PropertiesDialogViewModel等)は構造が単純なため下段にまとめて示す。 本図は初版(v1.0.0)時点のメンバー構成を示す。v1.1.0で追加されたメンバー (BusyProgress、MoveSelectionUp/Down、 PromoteLevel/DemoteLevel、CanUndo/UndoCommand等)の 詳細は関数リファレンスを参照。

継承 / has-a(コレクション・プロパティ)
再帰(自己参照ツリー)

図に描いていない関係: PdfFileEntryViewModel.ModelはCore.Models.PdfFileEntry、 BookmarkNodeViewModel.ModelはCore.Models.BookmarkNodeを1件ずつラップする (ドメインモデル図参照)。MainWindowViewModelはコンストラクタ経由で IPdfMetadataService・IPdfMergeService・IDialogService・ IUserSettingsService・ILogger<MainWindowViewModel>に依存する (UIヘッド図・Coreサービス図参照)。 3つのダイアログ用ViewModelはIDialogServiceの各実装(WpfDialogService / AvaloniaDialogService)がダイアログ表示のたびに生成し、Dispose()する。

04クラス図: UIヘッド(IDialogService / IUserSettingsService)

画面固有の処理はPdfBookmarkMerger.App.Services.IDialogServiceという1本の インターフェースに集約し、WPF版・Avalonia版がそれぞれ実装する。ThemeApplierは 両者が独立実装している静的クラスで、共通インターフェースは無い(意図的な設計。詳細は 設計ドキュメント参照)。

実装(implements)
依存(uses) — 設定ダイアログ確定時にテーマを適用

図に描いていない関係: WPF/Avalonia双方のConverters群(ZoomPercentToStringConverter等、 関数リファレンス参照)はIValueConverter/IMultiValueConverterを フレームワークごとに個別実装しており、共通インターフェースは持たない。

BookmarkDestinationType enum

XYZ / Fit / FitH / FitV の4種類のみをUIで選択可能とする。 PDF仕様上のバウンディングボックス指定(FitR/FitB系)は非対応で、 読込時にBookmarkDestinationTypeMapper.FromPdfSharpがFitBH→FitH・ FitBV→FitV・その他→Fitへ簡略化する。

PdfMergeService Services/PdfMergeService.cs

メソッド戻り値振る舞い・注意点
MergeAsync(PdfMergeRequest request, CancellationToken ct) Task Task.Run内で2フェーズに分けて実行する(v1.1.0で並列化・#1対応)。 フェーズ1(並列): SemaphoreSlim(MaxParallelOpen)で同時実行数を CPUコア数に応じて1〜8に制限しつつ、request.FilesをPdfReader.Openで 並列に開きopened[]配列へ格納する(出力側PdfDocumentへの 書き込みはスレッドセーフでないため、ここでは行わない)。 フェーズ2(単一スレッド): opened[]を順に output.AddPage(page)で1ページずつ取り込みながら (FileEntry.Id, 元ページ番号) → 出力先PdfPageの対応表(pageMap)を構築し、 ApplyBookmarksでrequest.Bookmarksを再帰的に辿って pageMapでジャンプ先ページを解決、出力ドキュメントのOutlinesを再構築。 最後にプロパティを設定し保存。ファイルパスではなくGuidのファイルIDをキーにするため、 同一PDFファイルを複数回結合対象に追加しても正しく動作する。 opened[]の各PdfDocumentは、フェーズ1・フェーズ2の両方を 囲む単一のtry/finallyでDisposeする(リリース前レビューで修正: 以前はフェーズ2の try/finallyにしか入っておらず、フェーズ1で1件でも PdfReader.Openが失敗すると、既に開けた他の正常なファイルがDisposeされず ファイルハンドルがプロセス終了までロックされたままになっていた)。
- ApplyBookmarks(target, nodes, pageMap) void 対応するページがpageMapに無いしおりは警告ログを出して読み飛ばす。 子を持つノードでは、子を再帰的に追加した後に outline.Elements.SetInteger("/Count", node.IsOpen ? childCount : -childCount)を 明示的に呼ぶ。PDFsharp 6.2.4の既知の不具合回避: document.Outlines直下(第1階層)以外のしおりについて、開閉状態を表す /Countを正しく書き込まない不具合があるため。

非破壊設計にした理由 #8対応

旧実装はMissingBookmarkFallback.EnsureEveryFileHasBookmarkが metadataByFileId内のPdfFileMetadata.Bookmarksへ直接 Addし、BookmarkOffsetCalculator.ComputeMergedBookmarksも 各ノードのMergedPageIndexを直接上書きする破壊的な設計だった。 単一スレッド・呼び出し毎に_metadataByFileId.Clear()する現在の使い方では実害が無いが、 「計算」を名乗るメソッドが入力を書き換える設計は、将来の再利用・並列化時に事故りやすいと判断し、 BookmarkNode.Clone()を新設して複製に対して計算するよう改めた。

MainWindowViewModel ViewModels/MainWindowViewModel.cs

メソッド戻り値振る舞い・注意点
ConfirmFilesAsync() internal Task 手順1→2の遷移処理。IsBusyを立て、SemaphoreSlimで 同時実行数をEnvironment.ProcessorCount(上限8)に制限しつつ、 FileList.Filesの各ファイルのIPdfMetadataService.ReadMetadataAsyncを 並列実行する(v1.1.0。旧実装はforeachによる逐次awaitで、 大量ファイル時にUIが長時間応答しない原因だった)。Task.WhenEachで完了順に結果を処理し、 そのつどBusyProgress(完了数/総数/処理中ファイル名)を更新する。 失敗したファイルはfile.MarkLoadFailed()でフラグを立て、 エラーダイアログを表示してスキップ(処理は継続)。成功したファイルのみ orderedFilesとしてまとめ、1件も無ければ Stepを遷移させずに早期return。 成功ファイルに対してMissingBookmarkFallback.ResolveEffectiveBookmarks→ BookmarkOffsetCalculator.ComputeMergedBookmarksの順に呼び、 結果をBookmarkTree.Loadに渡してStep = EditBookmarksへ遷移する。
MergeAsync() internal Task 手順4(結合)処理。#1対応: FileList.Filesから !f.LoadFailed.ValueのものだけをmergeTargetFilesとして フィルタし、ConfirmFilesAsyncのしおり計算対象と一致させる (フィルタしないと、しおりに含まれないファイルが結合には混入し、結合失敗やページオフセットのずれを招く)。 先頭ファイルのプロパティを既定値として保存先ダイアログ→(設定が有効な場合)プロパティダイアログを表示し、 いずれかでキャンセルされたら何もせず終了。PdfMergeRequestを組み立てて IProgress<MergeProgress>(v1.1.0)経由で進捗をBusyProgressへ 反映しながらIPdfMergeService.MergeAsyncを呼び、成功時は出力フォルダ・現在の Languageを含めてLastOutputDirectory等をユーザー設定に保存 (保存時にLanguageを引き継ぎ忘れると設定した言語が失われる不具合があったため注意)。 例外はcatchしてエラーダイアログに変換する。

コンストラクタではReactivePropertySlim/AsyncReactiveCommandを 使い、CombineLatestで各コマンドのCanExecuteを組み立てる (例: MergeCommandはStep==EditBookmarks && !IsBusyの間のみ実行可)。 BusyProgress(ReactivePropertySlim<BusyProgressInfo?>、v1.1.0)は IsBusyの間の詳細進捗を公開する。UI側は処理開始から5秒経過後にのみこの内容を表示する (DispatcherTimer、短時間処理での表示チラつき防止)。

09主要アルゴリズム解説

BookmarkTreeViewModel.Move — 並べ替え・再親子付け

しおりツリーのD&D並べ替えは、対象ノードを一旦削除してから挿入位置に再挿入する2段階操作だが、 同一コレクション内での移動の場合、削除によって後続要素のインデックスが1つ前に詰まるため、 挿入先インデックスの補正が必要になる。 

// 同一コレクション内かつ、移動対象が挿入先より前にある場合のみ補正する
if (ReferenceEquals(oldCollection, newCollectionBeforeRemoval))
{
    var oldIndex = oldCollection.IndexOf(node);
    if (oldIndex >= 0 && oldIndex < newIndex)
    {
        newIndex--;
    }
}

例: ルートに [A, B, C] があり、Aを「Cの後ろ」 (newIndex=3、末尾)へ移動する場合。AのoldIndex=0で 0 < 3なのでnewIndexを2に補正してから Remove→Insertする。補正しなければRemove後の コレクションは[B, C](要素数2)しか無いのにnewIndex=3を指定してしまい、 意図と異なる位置(または範囲外)に挿入されてしまう。

親を跨ぐ移動(再親子付け)では、削除元・挿入先それぞれの親のSyncChildOrderToModel()を 呼んでビュー側の並び順をCore.Models.BookmarkNode.Childrenへ反映する。 IsDescendantOfにより、ノードを自分自身の子孫の下へ移動しようとする操作は (親を辿ってnode自身に到達するかを確認して)無視する。

D&Dドロップ位置の判定(上半分/下半分)

WPF版のResolveBookmarkDropPlan(Avalonia版も同趣旨)は、カーソル位置が対象行の ヘッダー高さの上半分/下半分どちらにあるかで、挿入方法を切り替える。 

mouseWithinHeader.Y < headerBorder.ActualHeight / 2
  ? 上半分 → そのノードの子(先頭)として挿入(BookmarkTree.Move(dragged, targetNode, 0))
  : 下半分 → そのノードの直後の兄弟として挿入(newIndex = siblings.IndexOf(targetNode) + 1)

WPF版はさらにFindOwnHeaderBorderで「自分自身のヘッダー行(子として描画された ネストTreeViewItemの内部へは降りない)」を厳密に特定し、挿入位置インジケータ(BookmarkInsertionAdorner、 点+横線)の描画座標を計算する。何もない領域へのドロップは常にルート末尾への移動として扱う。

Avalonia版タイトル列インデント幅の食い違い(#2 プラットフォーム不具合の技術詳細)

設計ドキュメントに記載した不具合の技術的な原因と特定方法を記録する。 DepthToTitleWidthConverter.Convert(depth, baseWidth)は Math.Max(MinWidth, baseWidth - depth * IndentPerLevel)でタイトルTextBoxの幅を決める。 この式が正しく機能するのは、IndentPerLevelが実際にTreeViewItemが 1階層あたり適用する視覚的インデント幅と一致している場合のみである。

フレームワーク実際のインデント幅(実測)修正前のIndentPerLevel
WPF-UI (TreeViewItem既定スタイル)19px19px(正しい)
Avalonia FluentTheme (TreeViewItem既定テーマ)16px19px(誤り、WPF値を流用)

実測にはAvalonia.Headlessを使い、実際にMainWindowを構築して Dispatcher.UIThread.RunJobs()でレイアウトパスを走らせたうえで、 深さ0と深さ1のノードそれぞれについてタイトルTextBoxの TransformToVisual(treeView)による絶対座標を比較した。差分がちょうど16pxだったことから 実際のインデント幅を特定し、後続列(Left/Top/Zoom欄)の絶対X座標が深さに関わらず一致することを 修正前後で比較して検証した。 

// 修正前(誤り): depth=1のTextBox幅が19px縮むが、TreeViewの実インデントは16pxしか付かないため
// 差分3px分、後続列が深さに応じて右にずれていく。
private const double IndentPerLevel = 19;

// 修正後: Avalonia FluentThemeの実測値に合わせる。
private const double IndentPerLevel = 16;

併せて、幅の実測(MeasureTextWidth)がハードコードされた"Segoe UI"・ 13ptを使っていた点も修正した。Program.csのAppBuilder.WithInterFont()が アプリ全体の既定フォントをInterに設定しているため、実際にTextBoxが使うフォントは Avalonia.Media.Typeface.Default(内部的にFontManagerOptions.DefaultFamilyNameを 参照する)で取得すべきであり、フォントサイズもFluentThemeのControlContentThemeFontSize リソース(既定14)に合わせて14に修正した(いずれもヘッドレスアプリで Application.Current.TryGetResource・TextBox.FontSizeの実測値を確認して特定)。

PdfMergeService — 結合と/Countワークアラウンド

結合処理は「入力ファイルを順に開いてページを取り込みながら対応表(pageMap)を作る」 フェーズと、「編集済みしおりツリーを対応表で解決しながら出力ドキュメントに書き込む」フェーズに分かれる。 

pageMap: Dictionary<(Guid FileId, int OriginalPageIndex), PdfPage>

foreach (file in request.Files)
    foreach (page in file.Pages)
        pageMap[(file.Id, pageIndex)] = output.AddPage(page)

foreach (node in request.Bookmarks)   // 再帰
    outline = target.Add(node.Title, pageMap[(node.SourceFileEntryId, node.OriginalPageIndex)], node.IsOpen)
    // ... Left/Top/Right/Bottom/Zoom/DestinationTypeを反映 ...
    if (node.Children.Count > 0)
        ApplyBookmarks(outline.Outlines, node.Children, pageMap)   // 再帰後に↓
        outline.Elements.SetInteger("/Count", node.IsOpen ? childCount : -childCount)

ファイルID(Guid) + 元ページ番号をキーにしているため、同一PDFファイルを結合対象に 複数回追加しても(PdfFileEntry.Idが別なら)正しく別ファイルとして扱われる。 /Countの明示的な設定は、PDFsharp 6.2.4がdocument.Outlines直下 (第1階層)以外のしおりについて開閉状態を正しく書き込まない既知の不具合を回避するためのもので、 子を追加した後に呼ぶ必要がある(先に呼ぶと子の数がまだ確定していない)。

結合対象ファイルの整合性(#1)

ConfirmFilesAsyncは読込に失敗したファイルをorderedFiles (しおり計算対象)から除外するが、FileList.Files自体は変更しない。 修正前のMergeAsyncはFileList.Filesを無条件に結合対象へ使っていたため、 しおり計算では除外されたファイルが結合処理には混入するという不整合があった (壊れたPDFなら結合全体が失敗、一部だけ問題のあるPDFなら結合結果のページ数が想定より増え、 以降のファイルのしおりが指すページがずれる)。PdfFileEntryViewModel.LoadFailedフラグを 新設し、MergeAsync側も同じフラグでFileList.Filesをフィルタすることで、 しおり計算と結合実行の対象ファイル集合を常に一致させている (回帰テスト: MainWindowViewModelTests)。

10起動シーケンス

WPF版・Avalonia版とも、起動処理の骨格はPdfBookmarkMergerHostFactory.Buildに共通化されている。 

0. Program.Main (Avaloniaのみ、v1.1.0で追加)
     StartWithClassicDesktopLifetime(args) 全体をtry/catchで囲む
     → WPFのDispatcherUnhandledExceptionに相当するUIスレッド専用フックがAvaloniaには無いための埋め合わせ
     → catchした例外はLogUnhandledExceptionで記録してからrethrow(クラッシュ自体はさせる)

1. App()コンストラクタ(WPF: App.xaml.cs / Avalonia: App.axaml.cs)
     AppDomain.UnhandledException / TaskScheduler.UnobservedTaskException を登録
     (WPFのみ Application.DispatcherUnhandledException も登録)
     → Log.Logger 設定前の例外も、可能な限り早期に拾える状態にしておく

2. OnStartup / OnFrameworkInitializationCompleted
     PdfBookmarkMergerHostFactory.Build(args, configureUiServices) を呼ぶ
       a. AppPaths.AppDataDirectory / LogDirectory を作成
       b. Configuration: appsettings.json(実行ファイルと同じフォルダ) → settings.json(%AppData%/PdfBookmarkMerger/、reloadOnChange: true)
       c. Serilog: File(日次ローリング, 14世代保持) [+ Debugビルドのみ Console] を Log.Logger に設定
       d. DI: AddPdfBookmarkMergerCore() + AddPdfBookmarkMergerApp() + configureUiServices(IDialogService実装, MainWindow)
     host.Start()
     AppLanguageBootstrapper.ApplyAsync(userSettings) で表示言語を確定 (v1.1.0、MainWindow解決より前に実行必須)
     MainWindow を解決(DI構築、ここでXAMLのx:Static参照が確定する)
     ThemeApplier.Apply(...) でユーザー設定の表示モードを起動時に反映
     MainWindow を表示

3. OnExit / desktop.Exit
     host.StopAsync() → host.Dispose() → Log.CloseAndFlush()

configureUiServicesコールバックで、WPF版はWpfDialogService・ MainWindowを、Avalonia版はAvaloniaDialogService・ MainWindowをそれぞれAddSingletonする。 これによりPdfBookmarkMergerHostFactory自体はUIフレームワークを一切知らずに済む。

ArialFontResolver IFontResolver実装

コンソールアプリではPDFsharpのGDIベース既定フォント解決が働かないための最小限のリゾルバー。 GetFont(faceName)はEnvironment.GetFolderPath(SpecialFolder.Fonts) (実行環境のフォントフォルダ)からarial.ttf/arialbd.ttf/ ariali.ttf/arialbi.ttfを読み込む (以前はパスをC:\Windows\Fonts\...と直接ハードコードしていたが、 フォント未導入環境や別ドライブ構成での失敗を避けるためSpecialFolder.Fonts経由に変更した)。 ResolveTypeface(familyName, isBold, isItalic)は太字/斜体の組み合わせに応じて 4種類のうちどのフォントファイルを使うかを返す。
