Design Document for "PdfBookmarkMerger", a Multi-PDF File Merge Tool

A desktop application that merges multiple PDF files via drag & drop, automatically extracting and letting you edit each file's bookmarks (Outline) with page offsets applied, then writing the result out as a single PDF. The application layer, built around ReactiveProperty MVVM, is shared between two UI heads: WPF-UI (Windows) and Avalonia UI (macOS).

01Architecture

The application is split into three layers — "PDF reading/writing," "application logic," and "screens" — with only the screen layer implemented separately for the Windows and macOS builds. Because the application layer, including the ViewModels, is fully shared, feature additions and fixes made in one place are reflected on both operating systems.

PdfBookmarkMerger.Wpf

Screen-specific processing (file/folder selection dialogs, the properties dialog, message display) is consolidated into a single interface, PdfBookmarkMerger.App.Services.IDialogService, implemented by WpfDialogService on the WPF build and by AvaloniaDialogService on the Avalonia build. Because ViewModels depend only on this interface, the business logic has no knowledge of the UI framework whatsoever.

Design Decision Important

The WPF project's default namespace should originally have been PdfBookmarkMerger.Wpf, and the Avalonia project's PdfBookmarkMerger.Avalonia, but in both cases the trailing segment collided with the referenced library's own root namespace (Wpf.Ui.* / Avalonia.*), producing CS0234 ("The type or namespace name 'Ui'/'Controls' does not exist in the namespace 'PdfBookmarkMerger.Wpf'"). This stems from how C# name resolution searches outward from the innermost namespace for a "child namespace of the same name." As a workaround, the <RootNamespace> for each project was changed to PdfBookmarkMerger.WpfApp / PdfBookmarkMerger.AvaloniaApp respectively, avoiding the colliding segment name (the project names and output assembly names were left unchanged).

In addition to the three layers above, the solution includes an auxiliary project, tools/PdfBookmarkMerger.SampleGenerator. This is a developer-facing CLI tool that is not part of the distributed application; it regenerates, using PDFsharp, the sample PDFs used in tests/sample/ for testing (one with 3+ levels of bookmark hierarchy, and one with no bookmarks at all). Its purpose is to eliminate the need to recreate PDFs by hand and to let the structure of the sample PDFs (bookmark tree, coordinates, fonts) be version-controlled as code. It does not depend on PdfBookmarkMerger.Core (it performs page generation and bookmark creation directly via PDFsharp).

Application-Wide Exception Handling Policy Important

Individual asynchronous operations (metadata loading, running a merge, etc.) are wrapped in try/catch inside MainWindowViewModel and converted into log entries and error dialogs, but there had been cases where other unexpected exceptions (missed propagation from inside a binding, from an async lambda, etc.) caused the app to crash silently, leaving nothing in the log. A shared helper, PdfBookmarkMergerHostFactory.LogUnhandledException(Exception?, string source, bool flush), was introduced and is invoked by the WPF build from AppDomain.UnhandledException, Application.DispatcherUnhandledException, and TaskScheduler.UnobservedTaskException, and by the Avalonia build from the first and third of those (Avalonia has no equivalent of DispatcherUnhandledException) — recording as much as possible to Serilog before the crash and then calling Log.CloseAndFlush(). The flush argument lets the caller explicitly indicate "whether the process is about to terminate on this path"; note that setting it to true by mistake for a handler that keeps running afterward (unobserved task exceptions) causes all subsequent log entries to be silently dropped. To make up for the missing UI-thread-specific hook, v1.1.0 additionally wraps the entire StartWithClassicDesktopLifetime call in Program.Main for the Avalonia build in a try/catch (details).

04Domain Model

PdfBookmarkMerger.Core.Models is designed as plain POCOs with no dependency on PDFsharp types, to keep it easy to test.

BookmarkNode holds the complete information for a single bookmark

PropertyDescription
TitleThe bookmark's display text (editable)
SourceFileEntryId / OriginalPageIndexThe extraction-source file ID plus the zero-based page number within that file, identifying the jump-target page
MergedPageIndexThe zero-based page number in the merged output PDF (secondary information for display purposes)
DestinationTypeHow the GoTo action is displayed (Xyz/Fit/FitH/FitV/FitR/FitB/FitBH/FitBV)

Other Key Models

  • PdfFileEntry — A single file being merged (Id / FilePath / PageCount). Its position in the list directly determines the merge order.
  • PdfDocumentPropertiesModel — Title/Author/Subject/Keywords/Creator. Used when editing properties in the save dialog.
  • PdfFileMetadata — The extraction result for a single file (PageCount + the Bookmarks tree + Properties).
  • PdfMergeRequest — The full set of inputs to the merge process (Files / Bookmarks / Properties / OutputPath).

05Core Services

IPdfFileCollectorService file/folder expansion

Builds a list of PDF file paths from the paths passed in via drag & drop or a dialog (a mix of files and folders). When a folder is passed, only the files directly inside it are considered (SearchOption.TopDirectoryOnly); subfolders are not searched. Paths that don't exist and non-PDF files are ignored and simply logged, and processing continues.

IPdfMetadataService page-count and bookmark extraction

Opens the file with PDFsharp's PdfReader.Open(path, PdfDocumentOpenMode.Import) and recursively walks document.Outlines, converting it into a BookmarkNode tree. A PDF with no bookmarks at all simply returns an empty list without throwing. Bookmarks whose jump-target page cannot be identified (e.g. links to an external file) are skipped with a warning logged, and overall processing continues. The logic that looks up a page number from a jump-target PdfPage used to perform a linear scan of document.Pages for every single bookmark; this has been replaced with a reference lookup against a Dictionary<PdfPage, int> (using ReferenceEqualityComparer) built once, up front, in ReadMetadataAsync, so the cost stays linear even for PDFs with a large number of bookmarks or pages.

BookmarkOffsetCalculator / MissingBookmarkFallback cumulative page-offset calculation, non-destructive design

MissingBookmarkFallback.ResolveEffectiveBookmarks builds and returns a new "effective bookmark list per file" as a Dictionary<Guid, IReadOnlyList<BookmarkNode>>, filling in a bookmark titled after the file name (without extension) for any file that has no bookmarks of its own. The following step, BookmarkOffsetCalculator.ComputeMergedBookmarks, takes that effective bookmark list together with the file merge order and each file's page count, and computes each bookmark's MergedPageIndex as "the total page count of every file bound before this one, plus the page number within this file," writing the computed values onto a tree that has first been duplicated via BookmarkNode.Clone(), and returning that duplicate. Both steps follow a non-destructive design that never modifies the input (the original BookmarkNode collection cached as metadataByFileId), so recalculating or reusing the extracted bookmark data later never corrupts the source data. Files whose metadata could not be retrieved (load failures) are skipped from the result, and processing continues.

IPdfMergeService the merge itself

Creates an empty output PdfDocument, then opens each input file in turn with PdfDocumentOpenMode.Import and pulls in one page at a time via output.AddPage(page). While doing so it builds a mapping from (FileEntry.Id, original page index) → output PdfPage, then recursively walks the edited bookmark tree, resolving each jump-target page from that mapping, and rebuilds the output document's Outlines. Using each file's Guid ID as the key rather than its file path means the same PDF file can be added to the merge more than once and still work correctly. Finally, the properties are set and the document is saved.

Implementation Pitfall Caution

After Save() is called, PDFsharp's PdfDocument throws an exception on access to essentially any property, including PageCount ("The document was already saved and cannot be modified anymore."). When logging the page count in the merge-completion log entry, the value must be captured into a local variable — e.g. var totalPageCount = output.PageCount; — before calling Save().

Consistency of the Merge-Target File List Important

Files whose metadata fails to load in ConfirmFilesAsync have their LoadFailed flag set via PdfFileEntryViewModel.MarkLoadFailed() and are excluded from the bookmark-tree computation, but are not removed from the list itself (FileList.Files) — so they can be re-checked later. Because of this, MergeAsync applies the same filter, FileList.Files.Where(f => !f.LoadFailed.Value), so that the set of files used for the actual merge matches the set used to compute the bookmark tree. Skipping this would let a file that was excluded from the bookmark computation slip into the actual merge, causing a merge failure or a page-offset mismatch (regression test: MainWindowViewModelTests.MergeAsync_ExcludesFilesThatFailedMetadataLoad_...). Also, if not a single file loads successfully, ConfirmFilesAsync does not transition to WorkflowStep.EditBookmarks and stays on SelectFiles.

Undo Implementation v1.1.0

BookmarkTreeViewModel pushes a snapshot of the entire tree (List<BookmarkNode>, serialized to JSON) onto UndoHistory<string> immediately before any structural operation (add/remove/move/level change/level-cap truncation) and immediately before any node property edit (title, display method, coordinates, expanded state). Property edits are coalesced into a single edit when the same node's same property changes repeatedly within 800ms (e.g. one change per keystroke while typing). Once the total size of the history (the sum of each snapshot's UTF-8 byte count) exceeds the default 100MB cap, the oldest entries are discarded in order, keeping at least the single most recent entry (UndoHistory<T>.Push). "Set All to Fit" and "Set Expansion for All" are treated as temporary display-only overrides (the original values are restored automatically) rather than "edits" subject to Undo, so pushing a snapshot is suppressed via _suppressUndoSnapshots while either is being applied.

Two bugs were found and fixed during implementation. (1) ReactivePropertySlim.Subscribe replays the current value once immediately upon subscription (equivalent to a BehaviorSubject); a naive implementation therefore pushed a snapshot every time a node was created, even with no actual change, and because Undo itself rebuilds the tree, this caused the history to grow without bound. This was fixed with Skip(1) to exclude the initial replay. (2) Because BookmarkNode.Children is a read-only property with no setter, System.Text.Json ignores this property during deserialization by default, causing all descendants to be lost (child nodes disappearing after an Undo). This was resolved by explicitly applying the [JsonObjectCreationHandling(JsonObjectCreationHandling.Populate)] attribute (discovered via a direct JSON round-trip check; the existing Move/Undo tests had only ever exercised a flat structure, so they had not caught it).

Saving Settings (Configuration / Options)

PdfBookmarkMergerOptions (LastOutputDirectory / window size / Language, etc.) is loaded into Configuration at startup in two layers — appsettings.json (defaults) and settings.json (user settings, under %AppData%/PdfBookmarkMerger/, with reloadOnChange: true) — and supplied to the ViewModels via IOptionsMonitor<PdfBookmarkMergerOptions>. Setting changes (such as remembering the output folder used on a merge/save) are written back to the JSON file by IUserSettingsService.SaveAsync, and file-watching automatically triggers Configuration and Options to reload. Partway through v1.1.0 development the settings file was briefly moved to the same folder as the executable (to make the app portable), but since the executable's location may be read-only, it was ultimately unified with the log folder under %AppData%/PdfBookmarkMerger/ (details).

Bookmark settings file export New feature

The current bookmark tree can be exported, independently of running an actual PDF merge, as an XML file conforming to the internal "bookmark settings file specification" (a UTF-8 XML document whose root <Bookmark> element nests <Title Page="page-number display-method[ coordinates...]" Action="GoTo"> elements). A "Save Bookmark Settings File" button sits next to "Merge and Save PDF" on the bookmark-edit screen (step 3); once a save location is confirmed, BookmarkSettingsExportService.ExportAsync writes out the current bookmark tree (BookmarkTree.ToExportModel(), a non-destructive clone that also bakes in the cascading offsets from the page-number edits described below; it returns a Fit-only clone while Force Fit for All is on). The suggested file name reuses the merge dialog's default file name with its extension changed to .xml. The page number is the 1-based page within the merged PDF (MergedPageIndex, falling back to OriginalPageIndex when not yet computed); the display method is written with the same argument order as the PDF Reference's display methods (Fit/FitH/FitV/XYZ), substituting 0 for any unset Left/Top/Zoom argument (since the specification itself states that a Zoom of 0 means the same as null, this implementation applies the same convention to Left/Top to avoid shifting the argument positions).

Editable pre-merge page number New feature

The pre-merge page number shown in the bookmark tree's GoTo line ("From: {file name} p.N") changed from plain text to an editable text box (BookmarkNodeViewModel.PreOffsetPageNumber). Changing its value uniformly shifts the pre-merge page number of every bookmark in the same file whose underlying PDF page position (OriginalPageIndex) is at or after the edited row's — based on the source PDF's own page structure, not the bookmark tree's display order (BookmarkTreeViewModel.OnPreOffsetPageNumberChanged). The post-merge page number ("-> Merged p.N") of that same file, and of every file merged after it, cascades by the same total amount (ComputeCumulativeDeltaBeforeFile: a file's "total effect on later files" equals the delta carried by whichever of its bookmarks has the largest OriginalPageIndex, since every edit's affected range extends through that file's last page). This addend (BookmarkNode.PageOffset) never affects the OriginalPageIndex/MergedPageIndex fields the real PDF merge relies on — it exists purely for the bookmark-settings export and the on-screen display.

If an edit would push either the pre-merge or the post-merge page number below 1 (an inconsistency), both "Merge and Save PDF" and "Save Bookmark Settings File" are disabled. If there is no inconsistency, having at least one active edit disables only "Merge and Save PDF" (since the real merged PDF's page positions no longer match what is displayed or exported), while "Save Bookmark Settings File" stays available (BookmarkTreeViewModel's HasPageNumberEdits / HasPageNumberInconsistency are folded into the respective commands' CanExecute on MainWindowViewModel). Editing the value back to net zero re-enables both commands as usual.

The text box's width is not fixed — PageNumberWidthConverter computes it from the number of digits being displayed (including a sign), so the number is never clipped on a PDF with a large page count. A text box with a non-zero delta (i.e., an active edit) is highlighted with a semi-transparent amber background via EditedHighlightBrushConverter, reading BookmarkNodeViewModel.IsPageNumberEdited (a semi-transparent color was chosen, rather than an opaque one, so it reads correctly layered over both the light and dark themes). Right-clicking the text box opens a context menu with "Reset Pre-merge Page Numbers for This File"; choosing it calls BookmarkTreeViewModel.ResetFilePageNumbers, which clears the edits of every bookmark belonging to the same PDF file (SourceFileEntryId) as the row that was right-clicked, not just that one row (setting each bookmark's PageOffset back to its unedited state, null) Fixed in v1.2.0. Rolling back only the clicked row's own baseline value would leave earlier edits intact — edits applied to rows that sit before the reset target on the source PDF's own page structure — so the reset is scoped to the whole file instead. The reset is an Undo target too (a no-op, pushing no Undo entry, when that file has no active edits).

Responsiveness of edit/add/remove/undo operations on a large number of bookmarks Fixed in v1.2.1

The pre-merge page number cascade computation above (RecomputeAllPageNumberDisplaysAsync, formerly RecomputeAllPageNumberDisplays) walks the entire tree twice — once to compute the cross-file cumulative delta, once to write the result back to every node — on every operation that can change the tree (edit, add, remove, level-cap truncation, Undo, ...). With a large number of bookmarks, this walk (particularly the UI-binding updates triggered by writing each node's ReactivePropertySlim values) could occupy the UI thread for a long time, and because it ran fully synchronously, there was never a chance to even render an IsBusy indicator — the app appeared to freeze with no progress feedback at all.

The write-back loop is now split into chunks of BookmarkTreeViewModel.RecomputeChunkSize (200) nodes, but only when the node count exceeds that threshold; between chunks it yields to the UI thread via await Task.Yield(). During that time, the newly added BookmarkTreeViewModel.IsBusy/BusyProgress (the same BusyProgressInfo type already used for step 1's file loading) are updated, and MainWindowViewModel forwards them straight into its own IsBusy/BusyProgress — reusing the existing busy overlay and progress display from file loading instead of building new UI (the prior StatusMessage is saved off while forwarding is active and restored once it ends). That overlay covers the whole bookmark-edit screen and blocks mouse input, so there is no risk of the same recompute being re-triggered by another edit while a chunk is in flight. For trees at or below the threshold, the method never hits an await (it never reaches Task.Yield()) and completes synchronously exactly as before. Additional code review fix in v1.2.1 On top of that overlay-based protection, UndoCommand's own CanExecute now also requires CanUndo && !IsBusy, as defense in depth (it previously looked at CanUndo alone, leaving a theoretical path — e.g. a future keyboard shortcut — that could bypass the overlay and race the in-progress recompute).

The public signatures of the methods that used to call the recompute at their tail (AddRoot/AddChild/ AddSiblingAfter/Remove/Undo, etc.) are unchanged. They now go through a new private async void TriggerRecompute() (a fire-and-forget call that returns before the recompute necessarily finishes), so callers — code-behind and existing tests — needed no changes (for small trees the work is still effectively synchronous by the time control returns, so existing synchronous-call-site tests keep passing unmodified). Only SetChildLevelCapAsync, which was already async, awaits RecomputeAllPageNumberDisplaysAsync directly.

Partway through v1.1.0 development, a portable setup was tried where the settings file lived next to the executable so it would travel with it when moved or copied. Since the executable's location (e.g. under Program Files) may be read-only, it was ultimately unified with the log folder under the per-user AppData folder instead, where writes are guaranteed to succeed.

The Language field holds the result that AppLanguageBootstrapper auto-detects on first launch (details).

Writing User Settings (Atomic Writes)

Rather than overwriting settings.json directly with File.WriteAllTextAsync, UserSettingsService.SaveAsync writes to a temporary file in the same folder (settings.json.tmp) and then replaces the target via File.Move(overwrite: true). Because File.Move within the same volume is atomic, settings.json can never be left in a corrupted state (unparseable as JSON) if the process is forcibly terminated mid-write.

Logging Unhandled Exceptions

As described in the Architecture section, both the WPF and Avalonia startup paths (the App constructor) register AppDomain.UnhandledException and related handlers as early as possible, and record them to Serilog via PdfBookmarkMergerHostFactory.LogUnhandledException. Exceptions that occur before Host.Build() runs (before Serilog is configured) may not make it into the log, but exceptions that occur during normal operation are caught and recorded by this handler.

09Platform-Specific Notes

The ViewModel layer (PdfBookmarkMerger.App) is fully shared between WPF and Avalonia, but the look and layout on the XAML side depends on each UI framework's own default theme, so an implementation with the same intent can still surface as a bug due to differing defaults. Three such cases that actually occurred are recorded here.

Missing Default Binding for TreeViewItem.IsExpanded (Avalonia) Fixed

The WPF build explicitly sets <Setter Property="IsExpanded" Value="{Binding IsExpanded.Value, Mode=TwoWay}"/> in TreeView.ItemContainerStyle, but the Avalonia build's TreeDataTemplate has no way to bind IsExpanded, so this setting was missing entirely. As a result, the default value (true) of BookmarkNodeViewModel.IsExpanded was never reflected, and the bookmark editing tree always displayed fully collapsed. This was fixed by adding <Style Selector="TreeViewItem" x:DataType="vm:BookmarkNodeViewModel"> to TreeView.Styles in MainWindow.axaml, with the equivalent binding.

Mismatched Hierarchy-Indent Width in the Title Column (Avalonia) Fixed

DepthToTitleWidthConverter and RecomputeTitleColumnWidth keep the horizontal position of subsequent columns (display method, coordinates, etc.) aligned regardless of hierarchy depth, by subtracting "depth × per-level indent width" from the title column's width. The "per-level indent width" constant was reused as-is from the WPF-UI value (19px) in the Avalonia build as well, but the indent that Avalonia FluentTheme's default TreeViewItem actually applies is 16px — a 3px difference that pushed subsequent columns further right the deeper a node's hierarchy level (measured and identified by actually laying out a window with Avalonia.Headless and comparing each control's absolute coordinates). It was also found that the width measurement (MeasureTextWidth) was hardcoded to "Segoe UI" at 13pt, which did not match the Inter font at 14pt (ControlContentThemeFontSize) actually set as the default by .WithInterFont() in Program.cs; this too was fixed to use Typeface.Default at 14pt. Because of this history, the DepthToTitleWidthConverter golden test in PdfBookmarkMerger.UiConverters.Tests is designed to verify not that "the WPF and Avalonia computed results match," but that "each implementation computes correctly according to its own indent constant" (since the actual indent width genuinely differs between the two frameworks, requiring them to match would itself be wrong).

Clicking a bookmark row moves the horizontal scroll position (WPF and Avalonia both) Fixed in v1.2.1

Each row in the bookmark-edit tree is wide content — many controls laid out side by side — so when the window is narrow, a horizontal scrollbar appears (ScrollViewer.HorizontalScrollBarVisibility="Auto"). Clicking a row in that state triggered both WPF's and Avalonia's default "bring the target fully into view on selection/focus change" behavior, which tried to reveal the entire row (including its horizontal extent), moving the horizontal scroll position unexpectedly. Rewriting only the horizontal component of WPF's RequestBringIntoView routed event and re-requesting it was considered, but couldn't rule out the default "bring into view" handling running before the TreeView-level handler, at the ScrollViewer's own position along the event's bubble path — too unreliable to trust. Instead, the horizontal scroll position is captured right after the click (before selection processing begins), and restored once the whole selection/focus-change pipeline has settled — scheduled via DispatcherPriority.ContextIdle, draining the lower-priority queue first. This reliably preserves the horizontal position regardless of exactly which mechanism caused it to move (the default bring-into-view, or the Focus() call inside SelectBookmarkRowAtY, the fallback used when a row's margin — with no actual control — is clicked). The vertical position is left alone, so keyboard navigation that selects an off-screen row still scrolls it into view as before. Clicks on the horizontal scrollbar itself (ScrollBar) are excluded, so dragging it to scroll is never snapped back.

Japanese/English i18n Implementation Approach (x:Static + hand-written Strings.cs) v1.1.0

Resources/Strings.resx (Japanese, neutral culture) and Strings.en.resx (English satellite) live in PdfBookmarkMerger.App; the XAML side references them with {x:Static resx:Strings.SomeKey}, and the C# side directly with Strings.SomeKey (since both WPF's and Avalonia's x:Static extension are used the same way, the UI-layer code ends up nearly identical). Because dotnet build does not run the Visual Studio custom-tool code generation (ResXFileCodeGenerator) — confirmed empirically: the .resx file is compiled as an embedded resource, but Strings.Designer.cs is never generated — Strings.cs, which stands in for what that generated code would have been, is hand-written.

The display language is controlled via Strings.Culture (a static property). Rather than rewriting CultureInfo.CurrentUICulture, the culture is passed explicitly to ResourceManager.GetString(name, Culture), so number and date formatting and other locale-dependent behavior elsewhere are unaffected. AppLanguageBootstrapper.ApplyAsync runs before MainWindow is constructed (since x:Static references are fixed at the value in effect when the XAML is loaded): it uses the configured Language if one is set, otherwise determines Japanese vs. English from CultureInfo.InstalledUICulture (falling back to Japanese if detection fails or throws), persists the result via UserSettingsService.SaveAsync, and applies it to Strings.Culture.

On Maintaining the Two UI Heads in Parallel

The converters, the theme applier, and the dialog services are each implemented independently for WPF and Avalonia, so bugs of the "the defaults differ subtly" kind described above can happen again in the future. The golden tests in PdfBookmarkMerger.UiConverters.Tests are a countermeasure that lets conversion-logic behavior be verified mechanically whenever the code changes, but areas that involve actual window operations — D&D, Adorner rendering, dialog display — are costly to turn into automated tests, so the practice is to perform a visual check before each release using the UI Code-Behind Manual Verification Checklist.

11Windows Release Build Procedure (WPF-UI Edition)

scripts/publish-wpf-release.ps1 performs, in one pass, everything from the self-contained, single-file, compressed publish build for release through to zipping the result. The version number is picked up automatically from <Version> in Directory.Build.props at the repository root (the single source of truth), so the script itself never needs to duplicate a version number. 

# Run with defaults (win-x64, Release)
pwsh ./scripts/publish-wpf-release.ps1

# When specifying the runtime identifier and configuration
pwsh ./scripts/publish-wpf-release.ps1 -RuntimeIdentifier win-arm64 -Configuration Release

dotnet publish is invoked with -p:PublishSingleFile=true -p:EnableCompressionInSingleFile=true -p:DebugType=None, and the output is sent directly to dist/PdfBookmarkMerger-Wpf-v<Version>-<RID>/. Since dist/ is excluded from git via .gitignore, neither the extracted folder nor the zip archive is deleted afterward (the folder serves smoke-testing/direct-run purposes, and the zip serves distribution).

Constraints on WPF Single-File Publishing Caution

Even with single-file publishing, the native interop DLLs that handle WPF's rendering and input (wpfgfx_cor3.dll / PresentationNative_cor3.dll / D3DCompiler_47_cor3.dll / PenImc_cor3.dll / vcruntime140_cor3.dll — 5 files, roughly 7.8MB total) cannot be embedded into the exe, and are left alongside it in the same folder as appsettings.json (a known .NET SDK limitation with no workaround). So the distribution is not literally "a single exe and nothing else."
Measured sizes (win-x64, compressed, PDB excluded): approximately 70.5MB for the whole folder (about 62.6MB for the exe alone) / approximately 60.7MB after zipping. For comparison, an uncompressed, ordinary self-contained folder (without single-file) comes to 453 files and roughly 150.5MB. The exe was actually launched and confirmed to run correctly in this environment.

13Known Limitations and Future Work

  • PDFsharp 6.2.4 limitation on round-tripping the Outline expanded state (Opened) — When a PDF produced by this app is read back in, there is a known bug where the PdfOutline.Opened property itself cannot correctly interpret the sign of /Count (/Count itself is written correctly). This has been worked around by having both PdfMetadataService and PdfMergeService read and write /Count directly (every other field — title, hierarchy, jump-target page, etc. — already round-trips correctly).
  • No on-device verification on a real Mac — Only a successful cross-publish has been confirmed. Visual checks of D&D operations, window rendering, etc. have not been performed.
  • Code signing / notarization not configured — Packaging as a distributable .app, signing, and notarization remain future work.
  • Automated UI testing is only partial — The ViewModel layer (PdfBookmarkMerger.App.Tests) and the WPF/Avalonia converters (PdfBookmarkMerger.UiConverters.Tests) are covered by automated tests, but areas involving actual D&D operations, Adorner rendering, and dialog display still rely on visual confirmation via the manual verification checklist. Investigation for the Platform-Specific Notes confirmed that Avalonia.Headless can be used to verify layout results during individual bug investigations; whether to build this into a standing automated test is a matter for future consideration.
  • Drop-target behavior for bookmark D&D — A deliberately simple model was adopted where dropping onto a node always inserts as its child (at the end). Specifying an explicit "before/after" sibling insertion position is instead handled via the toolbar's "add as sibling," etc.
