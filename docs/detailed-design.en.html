PdfBookmarkMerger Detailed Design Document

Building on the architectural policy described in the Design Document, this document describes the actual class structure, the behavior of each function (method), and the key algorithms as they exist in the code. Class diagrams are embedded directly as SVG and show only the main members of each class (see the function reference tables in each section for the complete member lists).

BookmarkOffsetCalculator / MissingBookmarkFallback Non-destructive pipeline (fix for #8)

MethodReturn ValueBehavior & Notes
MissingBookmarkFallback.
ResolveEffectiveBookmarks(orderedFiles, metadataByFileId)		 Dictionary<Guid, IReadOnlyList<BookmarkNode>> Iterates over the files in order; for any file with zero bookmarks, CreateFallbackBookmark generates a single entry titled with the file name (without extension) to serve as its effective bookmark list (files that already have one or more bookmarks reuse the same instance as-is). The DestinationType used for a generated fallback inherits the "display method of the previous file's first bookmark" (coordinates are not inherited). If there is no previous file to reference, the default Fit is used. metadataByFileId itself is not modified (non-destructive).
- CreateFallbackBookmark(file, destinationType) BookmarkNode OriginalPageIndex = 0 fixed; all coordinate properties remain null
BookmarkOffsetCalculator.
ComputeMergedBookmarks(orderedFiles, effectiveBookmarksByFileId, metadataByFileId)		 List<BookmarkNode> Iterates over the files in order, duplicating each file's effective bookmarks with node.Clone(), applying ApplyOffset, and appending the result. offset is "the cumulative PageCount of the files bound before this one." Files whose metadata wasn't obtained (no key in metadataByFileId) are skipped. The input (nodes inside effectiveBookmarksByFileId) is not modified (non-destructive).
- ApplyOffset(BookmarkNode node, int offset) void Recursively applies node.MergedPageIndex = node.OriginalPageIndex + offset to itself and all descendants (since this is called on the post-Clone() copy, the original data is unaffected)

Why the design is non-destructive Fix for #8

The old implementation had MissingBookmarkFallback.EnsureEveryFileHasBookmark Add directly to PdfFileMetadata.Bookmarks inside metadataByFileId, and BookmarkOffsetCalculator.ComputeMergedBookmarks also directly overwrote each node's MergedPageIndex — a destructive design. This causes no real harm under the current usage (single-threaded, with _metadataByFileId.Clear() on every call), but a method that calls itself a "calculation" while mutating its input was judged prone to accidents in future reuse or parallelization, so BookmarkNode.Clone() was introduced and the calculation was changed to operate on the copy instead.

07Function Reference: App ViewModel Layer

MainWindowViewModel ViewModels/MainWindowViewModel.cs

MethodReturn ValueBehavior & Notes
ConfirmFilesAsync() internal Task Handles the transition from step 1 to step 2. Sets IsBusy, then runs IPdfMetadataService.ReadMetadataAsync for each file in FileList.Files in parallel while limiting concurrency to Environment.ProcessorCount (capped at 8) via a SemaphoreSlim (v1.1.0; the old implementation used sequential awaits in a foreach loop, which was the cause of the UI becoming unresponsive for long periods with large numbers of files). Task.WhenEach processes results in completion order, updating BusyProgress (completed count / total count / name of the file currently being processed) each time. Failed files are flagged via file.MarkLoadFailed(), an error dialog is shown, and processing continues, skipping that file. Only successful files are collected into orderedFiles, and if there are none, the method returns early without transitioning Step. For the successful files, MissingBookmarkFallback.ResolveEffectiveBookmarks is called followed by BookmarkOffsetCalculator.ComputeMergedBookmarks, and the result is passed to BookmarkTree.Load before transitioning to Step = EditBookmarks.
MergeAsync() internal Task Handles step 4 (merge). Fix for #1: filters FileList.Files down to only the entries with !f.LoadFailed.Value as mergeTargetFiles, matching the set used for bookmark computation in ConfirmFilesAsync (without this filter, files not included in the bookmarks would still be merged in, causing merge failures or page-offset drift). Shows the save-destination dialog with the first file's properties as defaults, followed by the properties dialog if that setting is enabled, and does nothing and returns if either is canceled. Assembles a PdfMergeRequest and calls IPdfMergeService.MergeAsync while reflecting progress into BusyProgress via IProgress<MergeProgress> (v1.1.0); on success, saves LastOutputDirectory and the like to user settings, including the output folder and the current Language (care is needed here — forgetting to carry Language forward when saving used to cause the configured language setting to be lost). Exceptions are catched and converted into an error dialog.

The constructor uses ReactivePropertySlim/AsyncReactiveCommand, assembling each command's CanExecute via CombineLatest (e.g., MergeCommand is only executable while Step==EditBookmarks && !IsBusy). BusyProgress (ReactivePropertySlim<BusyProgressInfo?>, v1.1.0) exposes detailed progress while IsBusy is set. The UI only displays this content once 5 seconds have elapsed since processing started (DispatcherTimer, to prevent display flicker for short-running operations).

09Key Algorithm Explanations

BookmarkTreeViewModel.Move — Reordering and Re-parenting

D&D reordering of the bookmark tree is a two-step operation: remove the target node and then reinsert it at the drop position. However, for a move within the same collection, the removal shifts the indices of subsequent elements down by one, so the insertion index needs to be corrected. 

// Correct only when moving within the same collection, and the moved item was located before the insertion point
if (ReferenceEquals(oldCollection, newCollectionBeforeRemoval))
{
    var oldIndex = oldCollection.IndexOf(node);
    if (oldIndex >= 0 && oldIndex < newIndex)
    {
        newIndex--;
    }
}

Example: the root has [A, B, C], and A is moved to "after C" (newIndex=3, the end). Since A's oldIndex=0 and 0 < 3, newIndex is corrected to 2 before performing Remove→Insert. Without the correction, the collection after Remove would only contain [B, C] (2 elements), yet newIndex=3 would still be used, inserting at an unintended position (or out of range).

For a move that crosses parents (re-parenting), SyncChildOrderToModel() is called on both the source and destination parents to reflect the view-side ordering into Core.Models.BookmarkNode.Children. Via IsDescendantOf, any attempt to move a node underneath its own descendant is ignored (by walking up the parent chain and checking whether node itself is reached).

Determining the D&D Drop Position (Upper Half / Lower Half)

The WPF version's ResolveBookmarkDropPlan (the Avalonia version follows the same idea) switches the insertion method based on whether the cursor position falls within the upper half or lower half of the target row's header height. 

mouseWithinHeader.Y < headerBorder.ActualHeight / 2
  ? Upper half → insert as that node's (first) child (BookmarkTree.Move(dragged, targetNode, 0))
  : Lower half → insert as the sibling immediately after that node (newIndex = siblings.IndexOf(targetNode) + 1)

The WPF version additionally uses FindOwnHeaderBorder to strictly identify "the row's own header row (never descending into a nested TreeViewItem rendered as a child)," and computes the drawing coordinates for the insertion-position indicator (BookmarkInsertionAdorner, a dot plus a horizontal line). A drop onto an empty area is always treated as a move to the end of the root.

Discrepancy in the Avalonia Title-Column Indent Width (Technical Detail of Platform Bug #2)

This records the technical root cause and how it was identified for the bug described in the Design Document. DepthToTitleWidthConverter.Convert(depth, baseWidth) determines the title TextBox's width via Math.Max(MinWidth, baseWidth - depth * IndentPerLevel). This formula only works correctly when IndentPerLevel actually matches the visual indent width that TreeViewItem applies per hierarchy level.

FrameworkActual Indent Width (Measured)IndentPerLevel Before the Fix
WPF-UI (default TreeViewItem style)19px19px (correct)
Avalonia FluentTheme (default TreeViewItem theme)16px19px (wrong — the WPF value was reused)

The measurement was taken using Avalonia.Headless: an actual MainWindow was constructed and a layout pass run via Dispatcher.UIThread.RunJobs(), then the absolute coordinates of the title TextBox (via TransformToVisual(treeView)) were compared for nodes at depth 0 and depth 1 respectively. Since the difference was exactly 16px, the actual indent width was identified this way, and it was verified — comparing before and after the fix — that the following columns' (Left/Top/Zoom fields) absolute X coordinates now match regardless of depth. 

// Before the fix (wrong): the depth=1 TextBox shrinks by 19px, but the TreeView's actual indent is only 16px,
// so the subsequent columns drift 3px to the right per level of depth.
private const double IndentPerLevel = 19;

// After the fix: matches the measured value for the Avalonia FluentTheme.
private const double IndentPerLevel = 16;

At the same time, the fact that the width measurement (MeasureTextWidth) used a hardcoded "Segoe UI" at 13pt was also fixed. Since Program.cs's AppBuilder.WithInterFont() sets the app-wide default font to Inter, the font actually used by the TextBox should instead be obtained via Avalonia.Media.Typeface.Default (which internally references FontManagerOptions.DefaultFamilyName), and the font size was also corrected to 14 to match the FluentTheme's ControlContentThemeFontSize resource (default 14) (both were identified by confirming measured values in a headless app via Application.Current.TryGetResource and TextBox.FontSize).

Non-Destructive Bookmark Preprocessing Pipeline (#8)

Call order and data flow within MainWindowViewModel.ConfirmFilesAsync: 

metadataByFileId (Dictionary<Guid, PdfFileMetadata>, not modified)
    │
    ├─▶ MissingBookmarkFallback.ResolveEffectiveBookmarks(orderedFiles, metadataByFileId)
    │       └─▶ effectiveBookmarks: Dictionary<Guid, IReadOnlyList<BookmarkNode>>
    │            (files with zero bookmarks are assigned a new list containing just one file-name bookmark;
    │             all other files point at the same instance as the one in metadataByFileId)
    │
    └─▶ BookmarkOffsetCalculator.ComputeMergedBookmarks(orderedFiles, effectiveBookmarks, metadataByFileId)
            └─▶ merged: List<BookmarkNode>
                 (an entirely new tree, built by Clone()ing each node in effectiveBookmarks and then setting
                  MergedPageIndex; neither metadataByFileId nor effectiveBookmarks is rewritten)

From BookmarkTree.Load(merged, fileNames) onward, even as the user edits the bookmark tree, only merged (the duplicate) changes, and the original extraction result cached in _metadataByFileId continues to be preserved. The current implementation does not reuse it, but this non-destructive property can serve as a foundation if a future "revert to pre-edit state" feature or similar is added.

PdfMergeService — Merging and the /Count Workaround

The merge process is split into a phase that "opens the input files in order and imports their pages while building a lookup table (pageMap)," and a phase that "writes to the output document, resolving the edited bookmark tree through that lookup table." 

pageMap: Dictionary<(Guid FileId, int OriginalPageIndex), PdfPage>

foreach (file in request.Files)
    foreach (page in file.Pages)
        pageMap[(file.Id, pageIndex)] = output.AddPage(page)

foreach (node in request.Bookmarks)   // recursive
    outline = target.Add(node.Title, pageMap[(node.SourceFileEntryId, node.OriginalPageIndex)], node.IsOpen)
    // ... apply Left/Top/Right/Bottom/Zoom/DestinationType ...
    if (node.Children.Count > 0)
        ApplyBookmarks(outline.Outlines, node.Children, pageMap)   // then, after the recursion:
        outline.Elements.SetInteger("/Count", node.IsOpen ? childCount : -childCount)

Because the key is file ID (Guid) + original page number, the same PDF file can be added to the merge target multiple times and (as long as PdfFileEntry.Id differs) is still correctly treated as a separate file. The explicit setting of /Count works around a known PDFsharp 6.2.4 bug where it fails to correctly write the open/closed state for bookmarks other than those directly under document.Outlines (the first level), and must be called after the children have been added (calling it beforehand means the child count is not yet finalized).

Consistency of the Merge-Target File Set (#1)

ConfirmFilesAsync excludes files that failed to load from orderedFiles (the bookmark-computation target), but does not modify FileList.Files itself. Before the fix, MergeAsync unconditionally used FileList.Files as the merge target, resulting in an inconsistency where files excluded from the bookmark computation still ended up mixed into the merge process (a fully corrupted PDF would fail the entire merge; a partially problematic PDF would inflate the merged page count beyond what was expected, causing subsequent files' bookmarks to point at the wrong pages). A PdfFileEntryViewModel.LoadFailed flag was introduced, and MergeAsync now also filters FileList.Files using the same flag, so that the file set used for bookmark computation and the one used for the actual merge always match (regression test: MainWindowViewModelTests).

ArialFontResolver IFontResolver implementation

A minimal resolver needed because PDFsharp's GDI-based default font resolution does not work in a console app. GetFont(faceName) loads arial.ttf/arialbd.ttf/ ariali.ttf/arialbi.ttf from Environment.GetFolderPath(SpecialFolder.Fonts) (the runtime environment's font folder) (previously the path was hardcoded directly as C:\Windows\Fonts\..., but this was changed to go through SpecialFolder.Fonts to avoid failures in environments without the font installed or with a different drive layout). ResolveTypeface(familyName, isBold, isItalic) returns which of the four font files to use based on the bold/italic combination.
