複数PDFファイル結合ツール「PdfBookmarkMerger」設計ドキュメント

複数のPDFファイルをドラッグ&ドロップで結合し、各ファイルのしおり(Outline)を ページオフセット付きで自動抽出・編集したうえで1つのPDFに書き出すデスクトップアプリケーション。 ReactiveProperty MVVM を核とするアプリケーション層を、WPF-UI(Windows)とAvalonia UI(macOS)の 2つのUIヘッドで共有する構成を採る。

.NET 10 C# 13 ReactiveProperty 9.9.0 Microsoft.Extensions.Hosting 10 Serilog WPF-UI 4.3.0 Avalonia UI 12.1.0 PDFsharp 6.2.4 (MIT) xUnit + Shouldly

01アーキテクチャ

「PDFの読み書き」「アプリケーションロジック」「画面」を3層に分離し、 画面層だけをWindows版・mac版で作り分ける。ViewModelまで含むアプリケーション層を 完全に共有することで、機能追加・修正が一箇所で両OSに反映される。

画面固有の処理(ファイル/フォルダ選択ダイアログ、プロパティダイアログ、メッセージ表示)は PdfBookmarkMerger.App.Services.IDialogService という1本のインターフェースに集約し、 WPF版は WpfDialogService、Avalonia版は AvaloniaDialogService がそれぞれ実装する。 ViewModelはこのインターフェースにのみ依存するため、ビジネスロジックはUIフレームワークを一切知らない。

設計判断 重要

WPFプロジェクトの既定名前空間は本来 PdfBookmarkMerger.Wpf、 Avaloniaプロジェクトは PdfBookmarkMerger.Avalonia となるはずだったが、 いずれも末尾セグメントがライブラリ自身のルート名前空間(Wpf.Ui.* / Avalonia.*)と衝突し、 CS0234(「型または名前空間の名前 'Ui'/'Controls' が名前空間 'PdfBookmarkMerger.Wpf' に存在しません」) が発生した。これはC#の名前解決が内側の名前空間から外側へ順に「同名の子名前空間」を探索する仕様に起因する。 対処として <RootNamespace> をそれぞれ PdfBookmarkMerger.WpfApp / PdfBookmarkMerger.AvaloniaApp に変更し、 衝突するセグメント名を避けた(プロジェクト名・出力アセンブリ名は変更していない)。

上記3層に加え、tools/PdfBookmarkMerger.SampleGenerator という補助プロジェクトを ソリューションに含めている。これは配布物には含まれない開発者向けCLIツールで、 tests/sample/ 配下のテスト用サンプルPDF(しおり3階層以上のものと、しおりを持たないもの)を PDFsharpで再生成する。手作業でPDFを作り直す必要をなくし、サンプルPDFの構成(しおりツリー・座標・フォント)を コードとして版管理できるようにするための位置づけ。PdfBookmarkMerger.Coreには依存しない (ページ生成・しおり作成のみを直接PDFsharpで行うため)。

アプリ全体の例外方針 重要

個々の非同期処理(メタデータ読込・結合実行等)はMainWindowViewModel内で try/catchしログ・エラーダイアログに変換しているが、それ以外の予期しない例外(バインディング内部・ 非同期ラムダの例外伝播漏れ等)によってアプリが無言でクラッシュし、ログに何も残らない事象があった。 PdfBookmarkMergerHostFactory.LogUnhandledException(Exception?, string source, bool flush) を共通ヘルパーとして設け、WPF版はAppDomain.UnhandledException・ Application.DispatcherUnhandledException・ TaskScheduler.UnobservedTaskExceptionから、Avalonia版は前者と後者2つから (Avalonia側にDispatcherUnhandledException相当のAPIは無いため)呼び出し、 クラッシュ前に可能な限りSerilogへ記録してからLog.CloseAndFlush()する。 flush引数は「この後プロセスが終了する経路か」を呼び出し側が明示するためのもので、 継続実行されるハンドラ(未観測タスク例外)で誤ってtrueにすると以降のログが一切書き込まれなくなる点に注意。 Avalonia版はUIスレッド専用フックが無い分の埋め合わせとして、v1.1.0でProgram.Mainの StartWithClassicDesktopLifetime呼び出し全体をtry/catchで囲む形で補強した (詳細)。

04ドメインモデル

PdfBookmarkMerger.Core.Models はPDFsharp型に依存しないプレーンなPOCOとして設計し、テスト容易性を確保している。

BookmarkNode しおり1件分の完全な情報を保持

プロパティ内容
Titleしおりの表示文字列(編集可)
SourceFileEntryId / OriginalPageIndexジャンプ先ページを特定する、抽出元ファイルID + ファイル内0始まりページ番号
MergedPageIndex結合後PDFにおける0始まりページ番号(表示用の副次情報)
DestinationTypeGoToアクションの表示方法(Xyz/Fit/FitH/FitV/FitR/FitB/FitBH/FitBV)
Left / Top / Right / Bottom / Zoomジャンプ先の表示座標・倍率(double?)
IsOpenしおりパネルでの初期展開状態
ActionType常に "GoTo"(PDFsharpが生成できるアクション種別は GoTo のみ)
Children子しおりのリスト(再帰構造)

その他の主要モデル

  • PdfFileEntry — 結合対象ファイル1件(Id / FilePath / PageCount)。並び順がそのまま結合順になる。
  • PdfDocumentPropertiesModel — Title/Author/Subject/Keywords/Creator。保存ダイアログのプロパティ編集に使用。
  • PdfFileMetadata — 1ファイル分の抽出結果(PageCount + Bookmarksツリー + Properties)。
  • PdfMergeRequest — 結合処理への入力一式(Files / Bookmarks / Properties / OutputPath)。

05Coreサービス

IPdfFileCollectorService ファイル/フォルダ展開

D&Dやダイアログで渡されたパス群(ファイル・フォルダ混在)から、PDFファイルパスの一覧を作る。 フォルダが渡された場合は直下のみ(SearchOption.TopDirectoryOnly)を対象とし、 子フォルダは検索しない。存在しないパス・非PDFは無視してログに記録するのみで処理は継続する。

IPdfMetadataService ページ数・しおり抽出

PDFsharpの PdfReader.Open(path, PdfDocumentOpenMode.Import) でファイルを開き、 document.Outlines を再帰的に辿って BookmarkNode ツリーへ変換する。 しおりが1件も無いPDFは空リストを返すだけで例外を投げない。ジャンプ先ページが特定できないしおり (外部ファイルへのリンク等)は警告ログを出して読み飛ばし、処理全体は継続する。 ジャンプ先PdfPageからページ番号を引く処理は、しおり1件ごとに document.Pagesを線形探索していた実装を、ReadMetadataAsyncの冒頭で 1度だけ構築するDictionary<PdfPage, int>(ReferenceEqualityComparer使用) による参照ルックアップに置き換えており、しおり数・ページ数が多いPDFでも計算量が線形に収まる。

BookmarkOffsetCalculator / MissingBookmarkFallback 累積ページオフセット計算・非破壊設計

MissingBookmarkFallback.ResolveEffectiveBookmarksは、しおりを1件も持たないファイルについて ファイル名(拡張子なし)をタイトルとするしおりを補った「ファイルごとの実効しおりリスト」を Dictionary<Guid, IReadOnlyList<BookmarkNode>>として新たに構築して返す。 続くBookmarkOffsetCalculator.ComputeMergedBookmarksは、その実効しおりリストと ファイルの結合順序・各ファイルのページ数から、しおりのMergedPageIndexを 「自分より前に綴じ込まれる全ファイルの総ページ数 + 自ファイル内のページ番号」として計算するが、 その際BookmarkNode.Clone()で複製したツリーに対して計算結果を書き込み、複製を返す。 いずれも入力(metadataByFileIdとしてキャッシュされている元のBookmarkNode群)を 変更しない非破壊設計であり、しおり抽出結果を後から再計算・再利用しても元データが壊れない。 メタデータ未取得(読み込み失敗)のファイルは結果からスキップされ、処理は継続する。

IPdfMergeService 結合本体

出力用の空 PdfDocument を作成し、各入力ファイルを順に PdfDocumentOpenMode.Import で開いて output.AddPage(page) で1ページずつ取り込む。 このとき (FileEntry.Id, 元ページ番号) → 出力先PdfPage の対応表を作りながら進め、 編集済みしおりツリーを再帰的に辿って対応表からジャンプ先ページを解決し、出力ドキュメントの Outlines を再構築する。ファイルパスではなく Guid のファイルIDをキーにすることで、 同一PDFファイルを複数回結合対象に追加しても正しく動作する。最後にプロパティを設定して保存する。

実装上の落とし穴 要注意

PDFsharpの PdfDocument は Save() 呼び出し後、 PageCount を含むあらゆるプロパティへのアクセスで例外 ("The document was already saved and cannot be modified anymore.")を送出する。 結合完了ログにページ数を出力する際は、Save() の前に var totalPageCount = output.PageCount; のようにローカル変数へ退避しておく必要がある。

06ViewModel層(PdfBookmarkMerger.App)

ReactiveProperty の ReactivePropertySlim<T> / AsyncReactiveCommand を用い、 WPF・Avalonia双方のBinding構文から等しく参照できる形でViewModelを実装している。

クラス役割
MainWindowViewModel手順1〜4の全体フローを統括する状態機械。WorkflowStep(SelectFiles / EditBookmarks)を持ち、CombineLatestで各コマンドのCanExecuteを組み立てる。BusyProgress(BusyProgressInfo?)で読込・結合の進捗を公開する
FileListViewModel結合対象ファイル一覧。追加・削除、単一/複数選択ブロックの一括並べ替え(MoveSelectionUp/MoveSelectionDown/MoveTo/GetMoveAvailability)
BookmarkTreeViewModelしおり編集ツリー。AddRoot/AddChild/AddSiblingAfter/Remove/Move/PromoteLevel/DemoteLevel。Moveは自分自身の子孫への移動をIsDescendantOfで防止。構造的な変更・プロパティ編集の直前にJSONスナップショットをUndoHistory<string>へ積み、UndoCommandで復元する(詳細)
BookmarkNodeViewModelしおり1ノード分の編集可能プロパティ(Title/DestinationType/IsOpen/Left/Top/Right/Bottom/Zoom)
PdfFileEntryViewModelファイル一覧1行分のViewModel。LoadFailed(メタデータ読込失敗フラグ)を持つ
PropertiesDialogViewModel / SettingsViewModel / LevelCapDialogViewModel各ダイアログ用の小さなViewModel

結合対象ファイルの整合性 重要

ConfirmFilesAsyncでメタデータ読込に失敗したファイルは、 PdfFileEntryViewModel.MarkLoadFailed()でLoadFailedフラグを立てたうえで しおりツリーの計算対象からは除外するが、一覧(FileList.Files)自体からは削除しない (再確認できるようにするため)。そのためMergeAsync側でも FileList.Files.Where(f => !f.LoadFailed.Value)で同じ判定基準を使い、 結合対象ファイル一覧をしおりツリーの計算時と一致させている。これを怠ると、しおりの計算には含まれない ファイルが実際の結合には混入し、結合失敗やページオフセットのずれを引き起こす (回帰テスト: MainWindowViewModelTests.MergeAsync_ExcludesFilesThatFailedMetadataLoad_...)。 またConfirmFilesAsyncは、読込に成功したファイルが1件も無い場合 WorkflowStep.EditBookmarksへ遷移せずSelectFilesのまま留まる。

元に戻す(Undo)の実装 v1.1.0

BookmarkTreeViewModelは、構造的な操作(追加・削除・移動・レベル変更・ レベル上限の切り詰め)の直前と、ノードのプロパティ編集(タイトル・表示方法・座標・開閉状態)の直前に、 ツリー全体(List<BookmarkNode>)をJSONへシリアライズしたスナップショットを UndoHistory<string>へ積む。プロパティ編集は、同一ノード・同一プロパティへの 800ms以内の連続変更(テキスト入力中の1文字ごとの変更等)を1回の編集としてコアレスする。 履歴の合計サイズ(各スナップショットのUTF-8バイト数の総和)が既定100MBを超えると、 最新の1件を除き最も古い履歴から順に破棄する(UndoHistory<T>.Push)。 「一律でFitに設定」「一律で展開表示を設定」は表示上の一時的な上書き(元の値は自動的に復元される)であり、 Undo対象の「編集内容」ではないため、これらの適用中は_suppressUndoSnapshotsで 履歴への積み増しを抑止する。

実装過程で2件の不具合を発見・修正した。(1) ReactivePropertySlim.Subscribeは 購読直後に現在値を1回リプレイする(BehaviorSubject相当)ため、素朴に実装するとノード生成のたびに 実際の変更なしでスナップショットが積まれ、Undo自体がツリーを再構築するため 無限に履歴が増殖する不具合になっていた。Skip(1)で初回リプレイを除外して解決した。 (2) BookmarkNode.Childrenはsetterを持たない 読み取り専用プロパティのため、System.Text.Jsonは既定では逆シリアル化時にこのプロパティを無視し、 子孫がすべて失われる(Undo後に子ノードが消える)不具合があった。 [JsonObjectCreationHandling(JsonObjectCreationHandling.Populate)]属性を 明示することで解決した(直接のJSONラウンドトリップ検証で発見。既存のMove/Undoテストはいずれも フラットな構造しか検証していなかったため検出できていなかった)。

設定の保存(Configuration / Options)

PdfBookmarkMergerOptions(LastOutputDirectory / ウィンドウサイズ / Language 等)は、起動時に appsettings.json(既定値)と settings.json(ユーザー設定、%AppData%/PdfBookmarkMerger/配下、 reloadOnChange: true)の2段階でConfigurationに読み込み、 IOptionsMonitor<PdfBookmarkMergerOptions> 経由でViewModelへ供給する。 設定変更(結合保存時の出力先フォルダ記憶など)は IUserSettingsService.SaveAsync が JSONファイルへ書き戻し、ファイル監視によってConfigurationとOptionsが自動的に再読み込みされる。 設定ファイルの保存先はv1.1.0の開発途中で一度実行ファイルと同じフォルダ(ポータブル化)へ変更したが、 実行ファイルの配置場所が読み取り専用の可能性を考慮し、最終的にログと同じ %AppData%/PdfBookmarkMerger/へ統一した(詳細)。

しおり設定ファイル出力 新機能

社内の「しおり設定ファイル仕様」(UTF-8のXML、ルート<Bookmark>直下に <Title Page="ページ番号 表示方法[ 座標...]" Action="GoTo">を入れ子で並べる形式)に 従ったXMLファイルを、実際のPDF結合を実行せずに単独で書き出せる。しおり編集画面(手順3)に 「結合してPDFを保存」と並べて「しおり設定ファイルを保存」ボタンを配置し、保存先ダイアログでの 確定後にBookmarkSettingsExportService.ExportAsyncが現在のしおりツリー (BookmarkTree.ToExportModel()、下記のページ数編集の連鎖分を反映した 非破壊な複製。ForceFitForAll適用中はFit一律の複製)を書き出す。 既定ファイル名は、PDF結合保存時の既定ファイル名の拡張子を.xmlに変えたもの。 ページ番号は結合後PDFにおける1始まりページ番号(MergedPageIndex、未算出の場合は OriginalPageIndexにフォールバック)、表示方法はPDF Referenceの表示方法 (Fit/FitH/FitV/XYZ)と同じ引数順で出力し、Left/Top/Zoomが未設定の引数は0を代入する(仕様上、Zoom=0は nullと同義とされているため、本実装ではLeft/Topにも同じ規約を適用して引数の位置ずれを避けている)。

結合前ページ数の編集 新機能

しおり編集ツリーのGoTo表示欄にある結合前ページ数(元: {ファイル名} p.N)を、テキスト表示から 編集可能なテキストボックス(BookmarkNodeViewModel.PreOffsetPageNumber)に変更した。 値を変更すると、同一ファイル内で、変更した行の元となるPDFページ位置(OriginalPageIndex)以降にある 全しおり(しおり編集ツリー上の表示順ではなく、あくまで元PDFのページ構造上の位置基準)の 結合前ページ数へ、差分が一律で加算される(BookmarkTreeViewModel.OnPreOffsetPageNumberChanged)。 あわせて、そのファイル自身および結合順で後に続くファイルの結合後ページ数(→ 結合後 p.N)も、 この差分をすべて合算した分だけ連動して変化する(ComputeCumulativeDeltaBeforeFile。 「そのファイル全体に効く差分」は、ファイル内でOriginalPageIndexが最大のしおりが持つ差分と等しい ——どの編集も自身の位置以降=最終ページを含む範囲に及ぶため)。この加算値 (BookmarkNode.PageOffset)は、実際のPDF結合が使う OriginalPageIndex/MergedPageIndexには一切影響しない、 しおり設定ファイル出力・画面表示専用の値である。

編集によって、結合前・結合後いずれかのページ数が1未満になる(不整合)場合は「結合してPDFを保存」 「しおり設定ファイルを保存」の両方を非活性化する。不整合が発生していなければ、編集が1件でもある間は 「結合してPDFを保存」のみを非活性化し(実際の結合後PDFのページ位置と画面表示・書き出し内容が 食い違うため)、「しおり設定ファイルを保存」は実行可能なままとする (BookmarkTreeViewModelのHasPageNumberEdits/ HasPageNumberInconsistencyをMainWindowViewModelの 各コマンドのCanExecuteに組み込む)。差分をすべて打ち消す値に戻すと、通常どおり両方とも活性化される。

ユーザー設定の書き込み(アトミック化)

UserSettingsService.SaveAsyncは、settings.jsonを直接 File.WriteAllTextAsyncで上書きするのではなく、同一フォルダの一時ファイル (settings.json.tmp)へ書き込んでからFile.Move(overwrite: true)で 置き換える。同一ボリューム内のFile.Moveはアトミックであるため、 書き込み途中でプロセスが強制終了してもsettings.json自体が壊れた状態(JSONとして パース不能)で残ることがない。

未処理例外のログ記録

アーキテクチャ節で述べた通り、WPF/Avalonia双方の起動処理(Appの コンストラクタ)でAppDomain.UnhandledException・ TaskScheduler.UnobservedTaskException等をできるだけ早期に登録し、 PdfBookmarkMergerHostFactory.LogUnhandledException経由でSerilogへ記録する。 Host.Build()実行前(Serilog未設定)の例外はログに残らない場合があるが、 通常運用中に発生する例外は本ハンドラで捕捉・記録できる。

WPF版はこれに加えてApplication.DispatcherUnhandledExceptionをUIスレッド専用の フックとして登録している。Avalonia(12.1.0時点)には同等のAPIが存在しないため (Avalonia.Base.dllを直接確認して不在を確認済み)、代わりに Program.MainのStartWithClassicDesktopLifetime呼び出し 全体をtry/catchで囲み、UIスレッドのイベントハンドラ等からメインループの外まで伝播した例外も 無言でクラッシュせず確実にログへ残るようにしている(v1.1.0で追加)。

09プラットフォーム固有の留意点

ViewModel層(PdfBookmarkMerger.App)はWPF・Avalonia間で完全に共有しているが、 XAML側の見た目・レイアウトはUIフレームワークごとの既定テーマに依存するため、 同じ意図の実装でも既定値の食い違いが不具合として表面化することがある。実際に発生した2件を記録する。

TreeViewItem.IsExpandedの既定バインディング欠落(Avalonia) 修正済み

WPF版はTreeView.ItemContainerStyleで <Setter Property="IsExpanded" Value="{Binding IsExpanded.Value, Mode=TwoWay}"/> を明示しているのに対し、Avalonia版のTreeDataTemplateにはIsExpandedを バインドする手段が無く、この設定自体が丸ごと抜けていた。結果として BookmarkNodeViewModel.IsExpandedの既定値(true)が 一切反映されず、しおり編集ツリーが常に折りたたまれた状態で表示される不具合になっていた。 MainWindow.axamlのTreeView.Stylesに <Style Selector="TreeViewItem" x:DataType="vm:BookmarkNodeViewModel">を追加し、 同様のバインディングを行うことで解決した。

タイトル列の階層インデント幅の食い違い(Avalonia) 修正済み

DepthToTitleWidthConverterとRecomputeTitleColumnWidthは、 タイトル欄の幅から「階層の深さ × 1階層あたりのインデント幅」を差し引くことで、表示方法・座標欄など 後続列の横位置を階層に関わらず揃えている。この「1階層あたりのインデント幅」定数をAvalonia版でも WPF-UIの値(19px)のまま流用していたが、Avalonia FluentThemeの既定TreeViewItemが 実際に適用するインデントは16pxで、3pxの差分が階層が深いノードほど後続列を右にずらしていた (Avalonia.Headlessでウィンドウを実際にレイアウトし、各コントロールの絶対座標を比較して実測・特定)。 併せて、幅の実測(MeasureTextWidth)がハードコードされた "Segoe UI"・13ptを使っており、Program.csの .WithInterFont()で実際に既定化されているInter・14pt (ControlContentThemeFontSize)と食い違っていた点も Typeface.Default・14ptを使うよう修正した。 この経緯から、PdfBookmarkMerger.UiConverters.Testsの DepthToTitleWidthConverterゴールデンテストは「WPF/Avaloniaの計算結果が 一致する」ことではなく、「各実装が自身の正しいインデント定数通りに計算しているか」を検証する形に 設計している(そもそも実際のインデント幅がフレームワーク間で異なる以上、一致するのが誤り)。

日英i18nの実装方式(x:Static + 手書きStrings.cs) v1.1.0

Resources/Strings.resx(日本語・中立カルチャ)と Strings.en.resx(英語サテライト)をPdfBookmarkMerger.Appに 配置し、XAML側は{x:Static resx:Strings.SomeKey}で、C#側は Strings.SomeKeyで直接参照する(WPF/Avalonia双方のx:Static拡張が 同じ書き方で使えるため、UI層のコードはほぼ同一になる)。dotnet buildは Visual Studioのカスタムツール(ResXFileCodeGenerator)によるコード自動生成を行わないため (実測で確認済み: .resxは埋め込みリソースとしてコンパイルされるが Strings.Designer.csは生成されない)、生成されるはずのコードに相当するものを Strings.csとして手書きしている。

表示言語はStrings.Culture(静的プロパティ)で制御する。 CultureInfo.CurrentUICultureを書き換える方式ではなく、 ResourceManager.GetString(name, Culture)に明示的にカルチャを渡す方式を採るため、 数値・日付書式など他のロケール依存処理に影響しない。AppLanguageBootstrapper.ApplyAsyncが MainWindow構築より前(x:Static参照はXAML読み込み時点で 値が固定されるため)に、設定済みのLanguageがあればそれを、無ければ CultureInfo.InstalledUICultureから日本語/英語を判定し(判定不能・例外時は日本語)、 判定結果をUserSettingsService.SaveAsyncで永続化したうえでStrings.Cultureに反映する。

2つのUIヘッドの並行保守について

Converter・ThemeApplier・ダイアログサービスはWPF/Avaloniaでそれぞれ独立して実装しており、 上記のような「既定値が微妙に異なる」種類の不具合は今後も起こり得る。 PdfBookmarkMerger.UiConverters.Testsのゴールデンテストは、変換ロジックの 挙動をコード変更時に機械的に検証できるようにするための対策だが、D&D・Adorner描画・ダイアログ表示など 実際のウィンドウ操作を伴う部分は自動テスト化のコストが高いため、 UIコードビハインド手動確認手順書による目視確認を リリース前に行う運用としている。

# ランタイム識別子・構成を指定する場合
pwsh ./scripts/publish-wpf-release.ps1 -RuntimeIdentifier win-arm64 -Configuration Release

dotnet publishは-p:PublishSingleFile=true -p:EnableCompressionInSingleFile=true -p:DebugType=Noneを指定し、出力先を dist/PdfBookmarkMerger-Wpf-v<Version>-<RID>/に直接向ける。 dist/は.gitignore対象(git管理外)のため、 展開済みフォルダ・zipアーカイブの両方を削除せずそのまま残す (フォルダは動作確認・そのまま実行する用途、zipは配布用の2用途)。

WPFの単一ファイル発行に関する制約 要注意

単一ファイル発行でも、WPFの描画・入力を担うネイティブ相互運用DLL (wpfgfx_cor3.dll / PresentationNative_cor3.dll / D3DCompiler_47_cor3.dll / PenImc_cor3.dll / vcruntime140_cor3.dll、計5ファイル・約7.8MB)はexeへ埋め込めず、 appsettings.jsonとともにexeと同じフォルダに残る(.NET SDKの既知の制約で回避不可)。 そのため「exe 1個のみ」の配布にはならない点に注意。
実測サイズ(win-x64, 圧縮あり・PDB除外): フォルダ全体 約70.5MB (exe単体 約62.6MB) / zip圧縮後 約60.7MB。比較として非圧縮の通常自己完結フォルダ (単一ファイル無し)は453ファイル・約150.5MB。本環境で実際にexeを起動し、 正常に動作することを確認済み。

12macビルド手順

本開発環境はWindows上のPowerShell/Bashのみで、実機のmacは利用できない。そのため クロスコンパイル・自己完結型パブリッシュの成功までを本環境で確認しており、 実機mac上でのウィンドウ表示・D&D操作等の目視確認は行っていない。配布前に実機での動作確認を推奨する。

Apple Silicon (arm64) 向け

dotnet publish src/PdfBookmarkMerger.Avalonia/PdfBookmarkMerger.Avalonia.csproj \
  -c Release -r osx-arm64 --self-contained true

Intel (x64) 向け

dotnet publish src/PdfBookmarkMerger.Avalonia/PdfBookmarkMerger.Avalonia.csproj \
  -c Release -r osx-x64 --self-contained true

本環境で osx-arm64 向けパブリッシュを実行し、 Avalonia.Native.dll を含むmacOS固有ランタイム一式が正しく出力されることを確認済み (src/PdfBookmarkMerger.Avalonia/bin/Release/net10.0/osx-arm64/publish/)。 実機macでの最終パッケージ化(.appバンドル化・コード署名・Notarization)は 今後の課題として 既知の制限事項 に記載する。

13既知の制限事項・今後の課題

  • PDFsharp 6.2.4のOutline開閉状態(Opened)往復に関する制限 — 自己出力したPDFを読み戻した際、PdfOutline.Openedプロパティ自体は /Count符号を正しく解釈できない既知の不具合がある(/Count自体は 正しく書き込まれている)。PdfMetadataService・PdfMergeService双方で /Countを直接読み書きすることで回避済み(タイトル・階層・ジャンプ先ページ等ほかの 全項目は元々問題なく往復する)。
  • mac実機での動作確認未実施 — クロスパブリッシュの成功までを確認。D&D操作やウィンドウ描画等の目視確認は未実施。
  • コード署名・Notarization未設定 — 配布用の.app化・署名・公証は今後の課題。
  • 自動UIテストは部分的 — ViewModel層(PdfBookmarkMerger.App.Tests)と WPF/Avalonia双方のConverter(PdfBookmarkMerger.UiConverters.Tests)は自動テスト化済みだが、 実際のD&D操作・Adorner描画・ダイアログ表示を伴う部分は 手動確認手順書による目視確認に依存している。 Avalonia.Headlessを使えば個別の不具合調査時にレイアウト結果を検証できることを プラットフォーム固有の留意点の調査で確認しており、恒常的なテストとして 組み込むかは今後の検討課題。
  • しおりD&Dの落下先仕様 — ノード上へドロップすると常にその子(末尾)として挿入する簡潔なモデルを採用。兄弟間の「前/後」挿入位置指定はツールバーの「兄弟として追加」等で代替する。
